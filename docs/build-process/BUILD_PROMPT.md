# CONFIG & PROMPT FILES
- Prompt file format: `prompts/<agent>/<name>.v<N>.md` with YAML frontmatter (`name`, `version`, `model_tier: fast|smart`, `temperature`, `response_schema` (Pydantic model path), `input_variables`, `cache_ttl`) and a Jinja2 body split into a `{# STATIC #}` section (system rules, taxonomy, tool schemas, few-shots; identical across calls) and a `{# DYNAMIC #}` section (user/request-specific data). `PromptRegistry` loads/validates files at startup (fails fast on missing variables), renders messages with the STATIC part FIRST (to maximize provider-side prefix caching), and exposes name+version+content hash for tracing and cache keys.
- `make prompts-sync` pushes prompts to Langfuse Prompt Management (files stay the source of truth) so each trace links to a prompt version. Local files are used if Langfuse is unreachable.
- Tests: every prompt referenced in code exists; all input variables are supplied; rendering is deterministic; no inline prompt text in `.py`.
- `config/taxonomy.yml` defines each system category with: `name`, `flow_type` (income|expense|transfer|savings), `nature` (fixed|essential_variable|discretionary|n/a), `description`, `examples`, `color`, `icon`. The same file feeds the categorizer prompt, the UI Categories page and the CSV template.

# AGENTS (each has its own job, prompt file(s), and tool set; none of them is "one prompt with different names")

## 1. Categorizer
Layered, cheapest first; each result stores `cat_source`, `cat_confidence`, `cat_rationale`:
1. **Normalizer** (strip POS/UPI/NEFT/IMPS prefixes, store numbers, dates, city/state, card digits; derive `merchant_norm`); 60+ unit-test descriptors across INR and USD.
2. **Merchant memory** (per user), then 3. **Rules** from `config/rules_lexicon.yml` + the user's keyword rules (sign/amount heuristics, e.g. positive + PAYROLL|SALARY → Income; accept only ≥ 0.85), then 4. **LLM fallback** (`MESH_MODEL_FAST`) over UNIQUE unresolved merchants, batches ≤ 25, strict JSON `{merchant_norm, category, subcategory, confidence, rationale}` validated against the user's enum, with the user's own labeled transactions as few-shot context. Confidence < 0.6 → `Uncategorized` + `needs_review=true` (a Review Queue in the UI) rather than guessing. 5. Write results to `merchant_memory`.
Prompt files: `prompts/categorizer/classify.v1.md` (static: rules + taxonomy; dynamic: merchants).

## 2. Analyzer (deterministic core; LLM only narrates in a separate step)
Findings with severity + evidence txn ids: monthly/weekly aggregates per category, MoM and trailing-3-month deltas; **anomalies** (robust z-score via median/MAD per category, merchant/category outlier transactions, first-time large merchants, duplicate charges within 3 days, price hikes on recurring items), each stating metric, baseline, observed, threshold crossed; **recurring detection** (period via median inter-arrival with tolerance, amount CV, ≥ 3 occurrences, ≥ 2 annual); **subscription audit** (monthly cost, total, flags `overlap`, `price_hike`, `low_value_proxy`; "unused" is NEVER asserted, only "likely unused (heuristic)" unless the user rated it 0–1 via `POST /subscriptions/{id}/usage`); **behavioral patterns** (weekend vs weekday, payday spike, late-night/impulse proxy, concentration, savings-rate trend, "latte factor" using the per-currency small-purchase ceiling). All thresholds from `config/thresholds.yml` and `currencies.yml`. `Analyzer.run(user_id, as_of)` returns a typed `AnalysisReport`, persists findings and refreshes `insight_snapshots`.

## 3. Forecaster (deterministic, the heart of the track)
Baseline daily cash-flow projection (default 90 days): (1) scheduled items from `recurring_rules` (declared) merged with `detected_recurrences` (declared wins) on their next dates; (2) discretionary spend per category (where `nature` is discretionary/essential_variable) as daily rate with day-of-week seasonality and payday effect, exponentially weighted (configurable half-life). **Monte Carlo** (2,000 seeded paths) bootstrapping historical daily residuals per category and perturbing recurring amounts by CV → p10/p50/p90 balance bands, month-end balances, P(balance<0), P(balance<buffer), projected monthly savings. **Goal projection** (ETA or shortfall; spend_cap projection). Two naive baselines (trailing-mean daily spend; last-month-repeat) for evaluation. Returns a serializable `ForecastResult` stored by reference in the trail. Must work with sparse data (< 2 months): returns a flagged low-confidence forecast with wider bands and a UI banner, not an error.

## 4. Simulator
Structured `Scenario` → delta vs the baseline by re-running the forecaster with the SAME seed. Types: `one_time_purchase`, `recurring_cost`, `cancel_subscription`, `income_change`, `savings_transfer`, `category_cut`, `loan_or_installments(total, n, apr)`, composites. Output: new min balance + date, end-of-horizon delta, change in overdraft probability, goal ETA changes, verdict by explicit rule (affordable if p10 stays above the buffer for the whole horizon; risky if p50 stays above but p10 dips below; not affordable otherwise), plus top-2 levers each verified by re-simulation. **NL entrypoint** ("can I afford a ₹80,000 trip next month?"): the fast LLM ONLY parses to a `Scenario` (schema-validated; missing slot → a clarifying question using a LangGraph interrupt that resumes from the Redis checkpoint), then the deterministic simulator runs, then the LLM verbalizes under the grounding guard (degraded: template).

## 5. Advisor
Builds candidate actions deterministically (cancel-subscription with exact monthly savings, category caps from baseline, delay-purchase timing, goal catch-up, fee pay-down, "promote this detected repeat"), each with `est_monthly_impact`, evidence ids, and a SIMULATED effect on the forecast/goal gap. Inputs also include long-term memory (preferences; previously dismissed recommendations and reasons so they are not repeated) and goal status. The smart LLM receives only ranked candidates + computed facts and must pick the top 3 and output `{recommendation_id, title, action, why, cited_finding_ids[], numbers_used[]}`. A validator rejects generic advice (needs ≥ 1 finding id and ≥ 1 specific entity: merchant, category, or date). Writes `recommendations` + `decision_trail` (trigger kind: anomaly | subscription | forecast_shortfall | goal_gap | pattern, finding ids, evidence txn ids, forecast reference, reasoning, model, prompt name+version, grounding report, Langfuse trace id).

## 6. Grounding guard (`trail/grounding.py`)
Extract every number, percentage, date and currency amount (INR/USD formats above) from LLM text; verify against the computed-facts set supplied in the prompt (tolerance ±1% or ±1 currency unit, from config). Unverifiable numbers → regenerate with an error message (max 2 retries) → fall back to a deterministic template from `templates/messages/`. Persist `{verified, unverified, retries}`; emit as Langfuse scores. Track the first-attempt pass rate.

## 7. Goal tracker (P1)
Weekly snapshots (progress, projected completion, on_track, gap). Behind → `goal_gap` findings drive catch-up actions with simulation; ahead → suggest reallocating surplus. Digests show the delta since the last snapshot.

## 8. Chat agent (P1) and Intent router (P0 for caching)
- **Intent router** (`config/intents.yml`): canonical intents such as `spending_trend`, `where_to_save`, `where_overspending`, `top_categories`, `upcoming_bills`, `subscription_review`, `goal_status`, `savings_rate`, `income_summary`, `afford_purchase` (non-cacheable → simulator), `free_form`. Match order: normalized-text rules/keywords → embedding similarity against example phrasings (if embeddings enabled) → fast-LLM classification. Each intent declares `handler` (`deterministic_template` | `llm_from_facts` | `tool_agent`), `ttl`, `time_relative` (true if "this month"-type, so the cache key includes the date bucket), and `needs_period` slot (default current month).
- **Chat agent**: tool-calling loop through Mesh with tools `query_transactions(filters, group_by)`, `get_category_trend`, `get_forecast`, `simulate(scenario)`, `list_subscriptions`, `get_goal_status`, `list_recurring`, `explain_recommendation(id)`, `recall_memory(query)`. Every number must come from a tool; max 6 iterations; the grounding guard runs on the final answer. UI streams tool-progress events (“Looking at your Dining Out spend…”) and delivers the final VERIFIED message (do not stream unverified text).

## 9. Memory writer (P1): see MEMORY.

# ORCHESTRATION (LangGraph) — `agents/coordinator.py`
Explicit graph: `ingest → categorize → analyze → forecast → goals → advise → persist_trail → snapshot → (deliver?)`, with conditional edges (skip categorize when nothing unresolved; skip LLM stages in degraded mode). A `route_intent` entry node: `{answer_from_cache, ask_affordability → simulator, free_chat → chat_agent, refresh_insights → full pipeline, explain → trail lookup}`. **State and checkpoints persist in Redis** via the LangGraph Redis checkpointer (thread_id = `user:{id}:run:{run_id}` or the chat session) so runs survive restarts and interrupts (clarifying questions) resume. Each node writes an `agent_runs` row and updates Redis `run:{run_id}` progress; the UI's Pipeline Trace polls it (SSE preferred). Each run is one Langfuse trace with a span per node (use the Langfuse LangChain/LangGraph callback handler). Graceful degradation: LLM/Mesh/embedding failure → rules-only categorization + "Uncategorized", templated advice from deterministic candidates, run flagged `degraded=true`, shown in UI and digest; degraded mode makes zero LLM calls.

# REDIS USAGE (namespaced, user-scoped, with TTLs)
`sess:`/`rl:` rate limits and token-revocation hints; `lg:` LangGraph checkpoints; `chat:{user}:{session}` short-term memory; `cache:llm:` response cache; `cache:ans:` insight/answer cache; `cache:lock:` single-flight locks; `dv:{user}` data_version mirror; `run:{run_id}` pipeline progress; `evalrun:{id}` eval progress; `lock:digest:`/`lock:beat:` scheduler/dedupe locks. Celery broker/results on DB 1/2. Everything in Redis except checkpoints must be reconstructible from Postgres (durable truth: data_version, digests, alerts, snapshots).

# CACHING (P0) — fast answers to the questions users ask most
Most questions are "how is my spending trend?", "where can I save more?", "where am I spending more?". Implement layered caching and measure it:
- **L0 Provider prefix caching**: prompts are STATIC-first/DYNAMIC-last (system rules, taxonomy, schemas, few-shots never change between calls), temperature 0 for structured tasks; record `cached_tokens` from usage into `llm_calls` and Langfuse (verify what Mesh passes through; do not assume).
- **L1 Exact LLM response cache** (`cache:llm:`): key = hash(model, prompt name+version, rendered messages, params), TTL by task; used for categorization batches, parsing, judge calls (makes evals reproducible and cheap).
- **L2 Insight/answer cache** (`cache:ans:`): key = `{user_id}:{intent}:{period}:{data_version}:{currency}:{locale}:{prompt_version}:{model}[:{date_bucket if time_relative}]`. A write that bumps `data_version` makes old entries unreachable (version-based invalidation, no scanning). Value = `{answer_text, facts, grounding, created_at}`. Responses show "Updated 2 h ago · instant answer" with a Refresh button.
- **L3 Semantic cache** (`semantic_cache`): for free-form phrasing close to a previously answered question of the SAME user and SAME data_version (cosine ≥ configurable 0.92 and same intent/period); disabled when embeddings are unavailable. Never share across users. Never cache `afford_purchase`, tool-agent answers involving user-specified amounts, or degraded answers.
- **Single-flight**: a Redis lock so concurrent identical misses trigger one computation.
- **Pre-warming**: after every pipeline run (and at login if stale), compute the top intents' answers from the fresh deterministic facts and store them in L2 and `insight_snapshots`, so the dashboard and quick-question chips respond instantly with no LLM wait. Deterministic-template intents need no LLM at all.
- **Observability**: log `cache_layer` (miss|L0|L1|L2|L3) per answer, show hit rate and p50/p95 latency by layer in the Evaluation screen, and push `cache_hit` scores to Langfuse. Targets: cached answer p95 < 300 ms server-side; dashboard < 1 s from snapshots.

# MEMORY (P1)
- **Short-term (Redis)**: last N turns (default 12) per chat session + rolling summary once it exceeds the token budget; pending slots for clarifying questions (via the LangGraph thread); TTL 24 h.
- **Long-term semantic memory: PostgreSQL + pgvector** (decision; reasons in DESIGN_NOTES: one fewer service, transactional with user data, user-filtered ANN is trivial at this scale, simple backup/delete-by-user; Qdrant is justified only at far larger scale). Hide it behind a `SemanticMemory` protocol so a Qdrant adapter could be added later. Embeddings come ONLY via Mesh (see rule 1) with the lexical fallback if unavailable.
- **What is stored**: durable facts and preferences ("saving for a Japan trip in March", "Netflix is shared with family — don't suggest cancelling", "income arrives irregularly", "prefers weekly digest on Sundays"), decisions and outcomes (recommendation accepted/dismissed + reason). NOT stored: account numbers, credentials, raw transaction dumps.
- **Writing**: the Memory writer (`prompts/memory_writer/extract.v1.md`, fast model, JSON schema) runs as a Celery task after a chat session goes idle (15 min) and on recommendation accept/dismiss. It extracts candidate memories with importance/confidence, dedupes (similarity > 0.9 → merge/update), supersedes contradictions, and applies expiry for time-bound facts.
- **Retrieval**: score = 0.6·similarity + 0.25·recency decay + 0.15·importance; top-k (default 5) within a token budget; injected in the DYNAMIC section (never the cached static prefix) inside `<memory>` data tags (untrusted). The advisor also receives dismissed-recommendation memories to avoid repeating itself.
- **Memory page** (UI): shows what FinPilot remembers, lets the user edit, pin or delete any memory or wipe all (privacy); deletion removes the vector row.

# OBSERVABILITY (Langfuse) (P0)
- `finpilot/observability/langfuse.py` initializes the v3 SDK from `LANGFUSE_HOST/PUBLIC_KEY/SECRET_KEY`; if unconfigured, no-op gracefully (never break the app). All LLM calls are traced through the wrapper in `llm/client.py`; agents/graph nodes/tools/cache lookups/DB-heavy steps use `@observe` or spans. Every trace carries `user_id` (hashed), `session_id` (chat session or run id), tags (`agent:<name>`, `env`, `eval`), and metadata (`data_version`, `cache_layer`, `degraded`, `prompt_name`, `prompt_version`, `currency`).
- **Masking**: a `mask` function redacts emails, phone numbers, long digit strings (account/card numbers) and, when `LANGFUSE_CAPTURE_CONTENT=false`, replaces message bodies with hashes. Document the privacy trade-off.
- **Scores on production traces**: `grounding_pass`, `grounded_number_ratio`, `cache_hit`, `user_feedback` (👍/👎 in the chat and on recommendation cards), `degraded`. Cost tracking: configure custom model definitions in Langfuse for the Mesh model names so cost appears.
- **Eval monitoring**: each eval run creates/updates a Langfuse Dataset per suite (items = test cases with expected outputs), runs the system against items linked to their traces (dataset runs/experiments, using the current SDK API), and attaches per-item and aggregate scores (accuracy, correct, abs_error, coverage_hit, judge_score…). Run name = `<suite>/<git_sha>/<timestamp>` so runs are comparable in Langfuse. Offline (no-LLM) evals also log their scores. The in-app Evaluation page deep-links to the Langfuse run/trace for each case.
- Optional (P2): configure Langfuse's own LLM-as-judge evaluators with an LLM connection that points at the Mesh base URL, so even that stays inside the Mesh rule.

# EVALUATION (heavily rewarded; real, stored in Postgres, monitored in Langfuse, shown in the UI)
**Data**: `eval/synth/generator.py` — seeded, ≥ 4 personas across BOTH currencies (e.g., USD salaried-stable, USD freelancer-irregular-income, INR salaried-with-EMI-and-SIP, INR overspender-with-subscription-creep) × 12–18 months, with ground truth: true category per transaction, true recurring series, injected anomalies (spikes, duplicates, price hikes, one-off large purchases) with ids, and held-out future months for backtests. Messy realistic descriptors (POS prefixes, UPI/NEFT strings, store numbers, typos), ~15% ambiguous merchants, and ≥ 30% of merchants absent from the rules lexicon and memory. Synthetic users are flagged `is_synthetic` and live in the same DB but are excluded from product features.
**Suites** (each in `eval/suites/`, each producing per-case rows + aggregate metrics; each runnable offline where it needs no LLM):
1. Categorization: accuracy, macro-F1, per-category P/R/F1, top confusions; per layer (rules / +memory / full), per persona/currency; share resolved per layer; LLM calls and cost per 1,000 txns; calibration by confidence bucket; accuracy on unseen merchants; **custom-category** test (user defines "Pet Care"/"Tuition" and the categorizer uses it); prompt-injection robustness test.
2. Forecast: rolling-origin backtest (≥ 6 origins/persona), horizons 7/30/60; MAE and sMAPE of end-of-month balance and monthly spend per category; p10–p90 interval coverage (target ≈ 80%); pinball loss; improvement vs both naive baselines; report honest losses.
3. Anomaly detection: P/R/F1 by type; false positives per month on clean personas.
4. Recurring/subscription detection: P/R, period accuracy, amount error, next-date error (days); materializer idempotency (no duplicates, correct catch-up).
5. Simulation: `hypothesis` property tests (adding a purchase never raises end balance; delta equals purchase at the deterministic mean; cancelling a subscription raises end balance by monthly × occurrences; same seed → identical; composites ≈ sum of parts) + a historical simulation backtest vs realized trajectory.
6. Advisor: % with ≥ 1 cited finding; grounding first-attempt pass rate; % specific; LLM-as-judge via Mesh (rubric in `prompts/eval_judge/`, mean score; rubric committed); personas yield different top recommendations; dismissed recommendations are not repeated (memory).
7. Cache & latency: hit rate on a simulated 200-question session mix; p50/p95 latency by layer; invalidation correctness (add a txn → next answer is a miss); cross-user isolation; cost saved.
8. Memory: retrieval hit@k on synthetic fact/question pairs; contradiction supersede correctness; deletion actually removes recall.
**Storage (Postgres)**: `eval_runs(id, started_at, finished_at, git_sha, trigger ['manual'|'ci'|'scheduled'], mode ['offline'|'full'], status, config_json, models_json, prompt_versions_json, langfuse_run_urls_json, summary_json)`, `eval_metrics(run_id, suite, metric, value, unit, dimension_json)` (long format for trending), `eval_cases(run_id, suite, case_id, input_json, expected_json, actual_json, passed, score, error_type, langfuse_trace_id)`, `eval_insights(run_id, severity, title, body, evidence_json, generated_by ['rules'|'llm'])`. Evals run as Celery tasks (admin button, CI, or nightly schedule) with live progress in Redis.
**Insights generation** (`eval/insights.py`): deterministic rules first — regressions vs the previous comparable run beyond tolerance, metrics below `config/thresholds.yml`, worst-performing categories/personas, calibration gaps, coverage far from 80%, places where the model loses to a baseline, cache hit-rate shortfalls, slowest agents — each with evidence. An optional LLM step (grounded, same guard) writes a short narrative from those facts only.
**Evaluation screen**: run selector and history; header with status, git sha, models and prompt versions, "Open in Langfuse"; KPI cards with deltas vs the previous run (green/red); tabs per suite (categorization: layer breakdown, per-category table, confusion heatmap, calibration chart, unseen-merchant accuracy; forecast: backtest table by persona/horizon, coverage vs target, improvement vs baselines, predicted-vs-actual chart; anomalies; recurring; simulation; advisor: grounding/specificity/judge distribution; cache & latency; memory); a **Failures explorer** (filter failing cases, see input/expected/actual, link to the Langfuse trace); trend charts across runs; and an **Insights panel** with the generated findings ordered by severity; compare-two-runs view; admin-only "Run evaluation" with live progress.
**Gating**: `make eval-offline` runs the deterministic suites against Postgres, writes results, and exits non-zero if thresholds in `config/thresholds.yml` are violated; `make eval` runs everything including LLM suites. Commit a real-run `eval/results/RESULTS.md` (generated from Postgres) and embed it in the README. Never invent numbers; if something was not run, say so.
